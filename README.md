# 予約リマインダー（Googleカレンダー × LINE）

AIエンジニア講座 課題2「Googleカレンダー×LINE予約リマインダー」の提出物です。

Googleカレンダーに登録された翌日の予約を毎日18:00（日本時間）に判定し、リマインダーを送るべき予約を自動で選び出します。

> **現在の到達点（最初にご確認ください）**
>
> - **LINEへの実送信は行っていません。** 送信は「シミュレーション」のみで、本文を作成して送信ログに記録するところまでです。LINEと通信するコード・SDK・設定は存在しません。
> - **Googleカレンダーへの実接続は検証していません。** カレンダーAPIの取得処理は実装済みですが、動作確認は偽のAPI応答（モック）を使ったテストで行っています。
> - 動作確認に使っているのは、すべて**架空の顧客・架空の予約**です。

---

## 1. プロジェクト概要と開発目的

### 背景
個人で営む予約制の店舗（美容室などを想定）では、予約をGoogleカレンダーで管理し、前日に手作業でリマインダーを送っていることがあります。毎日の確認と送信は手間がかかり、送り忘れや送り間違いの原因になります。

### 目的
- 翌日の予約から、リマインダーを送る相手を**自動で正しく選ぶ**
- 迷う予約（名前が合わない、登録されていない番号など）は**自動送信せず、人が確認する**
- 判定した後に予約が変わった場合は、**管理画面で気付ける**ようにする
- 個人情報や秘密情報を外に出さず、**誤送信が起きない安全な作り**にする

送信先をLINEにする前提で設計していますが、まず判定と管理の仕組みを完成させ、送信はシミュレーションで止めています。

## 2. 主な機能と予約判定の仕組み

### 主な機能

| 機能 | 内容 |
|---|---|
| 定時判定 | 毎日18:00（日本時間）に翌日の予約を判定します。18:10にも保険の実行があり、18:00の判定が成功していない場合だけ動きます |
| 送信シミュレーション | 通知対象の予約についてリマインダー本文を作り、送信ログに記録します（実際には送りません） |
| 二重送信の防止 | 同じ予約（予定ID＋開始日時）の送信ログは1件しか作られません。手動で再判定しても重複しません |
| 顧客マスタ | 顧客の登録・編集・論理削除。カルテ番号（4桁）は自動で振られ、変更・削除・再利用はできません |
| 表示名の自動生成 | 「田中様（0001）」の形式です。同じ姓の顧客がいる場合は全員を「田中(友)様（0002）」のように名の頭文字付きにします |
| 表示名の変更確認 | 登録・編集・削除で他の顧客の表示名まで変わる場合は、確認画面を挟みます |
| 判定後の変更検知 | 18:00の判定時点の記録と現在の予定を比べ、その後の「追加・変更・削除」を一覧にします。確認済みにした変更も、さらに変わればもう一度表示されます |
| 手動判定 | 管理画面から任意の日付で判定を実行できます |
| 管理画面 | ダッシュボード、判定結果、判定後の変更、送信ログ、顧客マスタ、手動判定の各画面があります |
| 月間送信数の表示 | 月ごとの送信数（シミュレーション）を、LINEの無料枠を目安にした200通と比べて表示します。80%に達すると警告します |

### 予約判定の仕組み

カレンダーの予定タイトルに含まれる **4桁のカルテ番号** と **表示名** を、顧客マスタと照らし合わせます。

```
予定タイトルの例:  田中(友)様（0002）
                    └─表示名─┘ └番号┘
```

全角・半角の違いと空白は、照らし合わせる前にそろえます（Unicode の NFKC 正規化と空白の除去）。

予定ごとに、次の順で「通知対象」「要確認」「対象外」の3つに分けます。

| 順 | 条件 | 結果 |
|---|---|---|
| 1 | キャンセルされた予定 | 対象外 |
| 2 | 終日の予定 | 対象外 |
| 3 | タイトルに4桁番号の括弧がない（私用の予定とみなす） | 対象外 |
| 4 | 番号が顧客マスタにない | **要確認** |
| 5 | 論理削除した顧客の番号 | **要確認** |
| 6 | 表示名が今の表示名と一致する | **通知対象** |
| 7 | 表示名が以前の表示名と一致する（同じ姓の顧客が増える前のタイトルなど） | **通知対象**（「タイトルが古い」という警告付き） |
| 8 | 番号はあるが、名前や敬称が一致しない | **要確認** |

- 対象日（日本時間）に始まる予定だけを判定します。前日から日をまたぐ予定などは除きます。
- 予定の説明欄に「メニュー: カット」のような行があれば、そのメニュー名を本文に入れます（最大50文字）。
- 説明欄はメニュー名を取り出すためだけに使い、判定の記録には保存しません。

### リマインダー本文（シミュレーション）

```
田中様 明日10月30日（金）10:00〜 カットのご予約を承っております。
```

宛名は「姓＋様」だけにしています。管理用の名の頭文字とカルテ番号は、顧客に見せないため本文に入れません。

## 3. 使用技術とシステム構成

### 使用技術

| 分類 | 技術 |
|---|---|
| 実行環境 | Cloudflare Workers（定時実行は Cron Triggers） |
| 言語 | TypeScript 5.9（strict モード） |
| Webフレームワーク | Hono 4.13（画面は Hono JSX でサーバー側で生成） |
| データベース | Cloudflare D1（SQLite） |
| 管理画面の認証 | Cloudflare Access（本番環境向け。Worker 側でも JWT を検証） |
| 予約の取得元 | 架空予定JSON（Fixture）／Google Calendar API v3（読み取り専用） |
| テスト | Vitest 4.1 ＋ @cloudflare/vitest-plugin（Workers ランタイム上で実行） |
| 開発ツール | Wrangler 4.151 |

### システム構成

```
            ┌───────── Cloudflare Workers ─────────────────────────┐
 Cron       │                                                      │
 18:00 ───▶ │  定時判定 ──▶ 予約の取得 ──▶ 判定 ──▶ 送信シミュレーション │
 18:10      │                  │                        │          │
 （保険）    │                  ▼                        ▼          │
            │       ┌─────────────────────┐        送信ログに記録      │
            │       │ Fixture（架空予定） │       （外部に送らない）    │
            │       │ Google Calendar API │                           │
            │       │ ※ローカル専用・未接続 │                           │
            │       └─────────────────────┘                           │
 管理者 ──▶ │  管理画面（Hono JSX）◀──▶ D1（顧客・判定・送信ログ・確認済み） │
（Access）  │                                                      │
            └──────────────────────────────────────────────────────┘
                       ✕ LINE への通信経路はありません
```

### ディレクトリ構成

```
src/
  domain/      判定・表示名・日付計算などの業務ルール（外部に依存しない）
  usecases/    定時判定、顧客管理、判定後の変更検知、画面用のデータ集計
  ports/       外部とのつなぎ口（インターフェース）
  adapters/    D1、Fixture、Google カレンダー、送信シミュレーションの実装
  web/         管理画面（ページ、認証ミドルウェア、ルーティング）
  lib/         ログ、再試行、外部通信の許可リスト
migrations/    D1 のテーブル定義
fixtures/      架空の顧客・架空の予約データ
test/          単体・結合・安全性テスト
```

業務ルール（`domain`）と外部とのやり取り（`adapters`）を分けているので、予約の取得元や送信方法を差し替えても判定のロジックは変わりません。

## 4. ローカルでの起動方法

### 必要なもの
- Node.js（開発時は v24 を使用）
- npm

Cloudflare アカウント、Google アカウント、LINE アカウントは不要です。既定の設定では、架空データだけで動きます。

### 手順

```sh
# 1. 依存パッケージをインストール
npm install

# 2. ローカル用の環境変数ファイルを作る（.dev.vars は Git に含まれません）
cp .dev.vars.example .dev.vars
#    → ENVIRONMENT=local だけが有効になっています。Google 連携の行はコメントアウトのままで動きます

# 3. ローカルの D1 にテーブルを作る
npm run db:migrate:local

# 4. 開発サーバーを起動
npm run dev
#    → http://localhost:8787 で管理画面が開きます
```

- ローカル（`ENVIRONMENT=local`）では、管理画面の Cloudflare Access 認証を省略します。
- `wrangler.toml` の既定は `ENVIRONMENT = "production"` です。`.dev.vars` でローカルを指定したときだけ、認証が省略されます。

### 主な設定値

| 変数 | 既定値 | 説明 |
|---|---|---|
| `ENVIRONMENT` | `production`（`.dev.vars` で `local`） | `local` のときだけ認証を省略し、架空データの投入を許可します |
| `SEND_MODE` | `simulation` | **`simulation` 以外の値では起動しません** |
| `CALENDAR_SOURCE` | `fixture` | `fixture`（架空予定）または `google`（ローカル専用） |
| `CALENDAR_ID` / `GOOGLE_ACCESS_TOKEN` | なし | `CALENDAR_SOURCE=google` のときだけ必要です（下記参照） |
| `ACCESS_TEAM_DOMAIN` / `ACCESS_AUD` | なし | 本番環境の管理画面認証用です（ローカルでは不要） |

#### 参考：Google カレンダー連携（未検証）
`CALENDAR_SOURCE=google` は `ENVIRONMENT=local` のときだけ使えます。本番環境で指定すると起動しません。

想定している方式は `.dev.vars.example` に書いた手順のとおりで、秘密鍵は作りません。
- gcloud でテスト用サービスアカウントの権限を借り、`calendar.readonly` の短時間トークン（約1時間有効）を発行します。
- そのトークンを `GOOGLE_ACCESS_TOKEN` に設定します。

**この方式で実際の Google カレンダーに接続して動作を確認したことはありません。**

## 5. 架空データを使った操作・検証方法

### 架空データ
- `fixtures/customers.json`：架空の顧客7名。同じ姓、似た漢字の姓（斉藤／斎藤）、論理削除する顧客を含みます。

### 操作の流れ

```sh
# 1. 架空の顧客を投入（ローカル専用。顧客がすでにいる場合は何もしません）
curl -X POST http://localhost:8787/dev/seed

# 2. 定時判定を手元で起動（npm run dev は --test-scheduled 付きで起動します）
curl "http://localhost:8787/__scheduled?cron=0+9+*+*+*"
```

| 画面 | パス | 確認できること |
|---|---|---|
| ダッシュボード | `/` | 翌日の判定状況と件数、月間送信数、判定後の未確認の変更、失敗した判定、最近の表示名の変更、カルテ番号の上限警告 |

## 7. セキュリティ対策

### 誤送信の防止
- 送信モードは `simulation` だけを許可しています。設定でも、DB の制約でも、それ以外を受け付けません。
- 送信の実装はシミュレーション（`SimulatedSender`）だけで、外部とは通信しません。
- 安全性テストで、次のものがソースコードに含まれないことを確認しています。
  - LINE の API ドメインと SDK
  - チャネルアクセストークンやシークレットの変数
  - Webhook の署名ヘッダー
- 迷う予約は「要確認」にして、自動では送信しません。

### 外部通信の制限
- 外部との通信は、許可リスト付きの関数（`src/lib/egress.ts`）を通す決まりにしています。
  - 許可しているのは Google の API ドメインだけで、通信は HTTPS に限ります。
  - 安全性テストで、この関数以外から直接 `fetch()` を呼んでいないことを確認しています。
- 架空データを投入してから判定、全画面の表示、顧客操作までを通しで行い、外部通信が1件も発生しないことをテストで確認しています。
- Google カレンダーは読み取り専用（`calendar.readonly`）を想定しています。取得するのは判定に必要な項目だけで、参加者のメールアドレスなどは受け取りません。

### 秘密情報の管理
- 秘密鍵は作らない方式にしています（短時間トークンを、ローカルでだけ使う）。
- `.dev.vars`、`.env*`、`*.pem`、`*service-account*.json` は `.gitignore` で除外しています。
- 安全性テストで、次のものがリポジトリ内のファイルに含まれないことを確認しています。
  - 秘密鍵、API キー、各種トークンの形式
  - 例示用以外のメールアドレス
  - 電話番号
- `wrangler.toml` に秘密情報を平文で書いていないことも、テストで確認しています。

### 管理画面の保護
- 本番環境では Cloudflare Access の JWT を Worker 側でも検証します（RS256、発行元とオーディエンスを確認）。
- 認証の設定が欠けている場合は、すべてのリクエストを拒否します。
- CSRF 対策（Hono の `csrf` ミドルウェア）を入れています。
- セキュリティヘッダーを付けています。
  - 外部リソースを読み込まない CSP（nonce 付き）
  - iframe への埋め込み禁止
  - Referrer を送らない
- 架空データの投入（`/dev/seed`）は、ローカル環境でしか使えません。

### 個人情報の保護
- ログに出せる項目を型で限定しています。顧客はカルテ番号だけで識別し、氏名・本文・予定タイトルはログに出しません。テストでも確認しています。
- エラーの詳細は、画面にもログにも出しません。
- 予定の説明欄は保存しません。
- 動作確認には架空データだけを使っています。
